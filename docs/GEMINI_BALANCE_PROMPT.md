# Gemini 구현 요청: 기존 기록을 보존하는 챌린지 밸런스

첨부한 최신 실제 파일을 기준으로 구현해주세요. 사용자와 Codex는 Windows에서 개발하고 최종 Xcode/iPhone/TestFlight만 Mac mini에서 진행합니다. 큰 구현은 Gemini가 작성하고 Codex가 검토·통합·테스트합니다. 제공되지 않은 지식 파일을 읽었다고 주장하지 마세요.

## 이번에 완성할 기능

`docs/BALANCE_PLAN.md`가 범위, `docs/BALANCE_CANDIDATE.json`이 새 미션·외형·발사 간격의 수치 원본입니다. `docs/BALANCE_AUDIT.md`는 수학적 가정의 보고서이며 플레이테스트 결과가 아닙니다. 후보 JSON을 fetch해 런타임에서 쓰지 말고 필요한 값을 기존 모듈과 작고 순수한 발사 간격 모듈로 통합하세요. 무조건 시간을 끄는 minimum-duration 완료 조건은 만들지 마세요.

1. 기존 m1~m6의 ID·목표·첫 보상·별점·발사 규칙을 그대로 두고 m7~m12를 추가하세요. 기존 기록의 비교 가능성을 유지하기 위해 피해량/비행 속도/크레이터 크기를 전역 변경하지 않습니다. 새 챌린지에만 pacing profile `challenge-v1`을 지정하세요. 샌드박스는 그대로 자유 발사입니다.
2. 새 챌린지 전용 발사 간격을 구현하세요. 운석 700ms, 레이저 450ms, 미사일 1100ms입니다. 한 발을 발사하면 다음 발사 가능 시각을 모든 무기에 공유해 무기 전환으로 우회할 수 없게 하세요. 순수 상태 모듈과 주입 시간으로 테스트할 수 있게 하고 Three.js 객체를 그 모듈에 넣지 마세요. 발사 판단은 한 곳에서 수행하고 main과 WeaponSystem 양쪽에서 중복으로 대기를 소모하지 마세요.
3. 미션 활성 시간 시계를 사용하세요. 일시정지 중 대기가 소진되면 안 됩니다. 첫 발사는 즉시 가능하며 cooldown 정확한 경계에서는 허용합니다. 잘못된 타깃·타입·정지·완료 후 입력은 소모하지 않습니다. 실제 발사 승인 후에만 효과음·발사체·동기 레이저 impact를 만드세요. 거부된 입력으로 소리·햅틱·impact·저장 요청이 생기지 않아야 합니다. 새 런·모드 변경·미션 종료·Reset은 관련 발사 상태를 정리하지만 단순 무기 선택은 정리하지 않습니다.
4. 기존 count/damage 목표를 유지하며 `req.targetCounts`와 `req.weaponCounts`의 모든 조건을 AND로 판정하도록 확장하세요. m11은 미사일로 targetIndex 1과 2를 각각 15회, m12는 운석 12회/레이저 18회/미사일 10회입니다. req.weapon·제외 천체·유효 무기·천체·runId 검사를 통과한 impact만 진척시킵니다. 목표에 없는 타격이 목표 카운터를 증가시키면 안 됩니다. 전체 count/damage와 세부 카운터를 일관되게 유지하세요. 저장 보상 검증의 isGoalReached도 같은 목표 규칙을 적용해야 하며, 한 조건만 채운 조작된 completion을 받아들이면 안 됩니다. snapshot은 중첩 카운터까지 복사해 호출자가 라이브 상태를 바꾸지 못하게 하세요.
5. 기존 UI의 `mission.req.count || mission.req.damage`만 참조하는 코드로는 복합 목표가 표시되지 않습니다. 입문/챌린지 구분, m11 두 천체별·m12 세 무기별 진척과 챌린지 재사용 대기를 명확히 표시하세요. 천체는 '안쪽 작은 행성'과 '바깥 큰 행성'으로 설명하고 색상만으로 구분하지 마세요. 잠금/로그인/광고 진입 조건을 만들지 말고 모두 선택 가능하게 하세요. HUD를 매 프레임 재생성하지 않고 시간·대기 텍스트는 읽기 좋은 단위로 갱신하세요. 대기 중 탭마다 에러 팝업을 띄우지 마세요. 목록 12개, 결과, HUD, 상점이 320px 화면에서 넘치지 않게 하세요.
6. 기존 4개 외형의 ID·가격·팔레트를 유지하고 신규 팔레트 외형 glacier/dune/nebula를 각 700/900/1100코인으로 추가하세요. 기존 SHOP_ITEMS와 같은 필드·palette 키를 사용하고 외형 장착 시 타격 흔적 보존을 유지하세요. 외부 이미지·3D 에셋·새 패키지는 필요하지 않습니다. 가능한 경우 첫 다음 미소유 외형과 필요한 코인을 상점에서 읽기 쉽게 안내하되 구매를 강제하지 마세요.
7. v6 payload·저장 키·기존 보상/보너스 원장·기존 최고기록·설정 키는 유지하세요. 추가된 미션/외형 ID를 정규화에서 정상 수용하되 미래 버전·읽기 실패 보호와 순차 불변 저장은 보존하세요. 신규 복합 카운터·발사 대기는 런타임 전용으로 저장하지 않습니다. 새 미션 첫 완료 보상은 후보 JSON 값이고 총 보상 4050 = 전체 외형 가격 4050코인입니다. 반복 보상 0·별점 추가 보상 없음·기존 whenSaved 계약을 유지하세요.

## 반드시 보존할 경계

- MonetizationController/AdPolicy/config·실제 네이티브 SDK·상품/광고 ID는 변경하지 마세요. 기존 null/off 기본값, 첫 완료 저장 성공 이후에만 광고 제안, 보상 1회, 전면 광고 유예/횟수/재도전 제외 규칙은 유지합니다. 새로운 미션 ID에도 기존 정책을 적용하되 코인 소비·광고 시청으로 대기를 단축하는 기능은 추가하지 않습니다.
- 앱이 자체 서버 없이 오프라인에서 작동해야 합니다. Game Center·Firebase·RevenueCat·분석 SDK·일일 보상·가챠·IAP 추가·클라우드 랭킹은 이번 범위에 없습니다. HubGame 전용 UI 조건부 노출과 별개로 로컬 게임 저장/상점은 계속 동작합니다.
- 기존 완료/기록을 초기화하거나 완료 미션을 새로 보상하지 마세요. 기존 입문 기록을 새 챌린지 기록으로 복사하지 마세요. 변경 파일을 과거 버전으로 되돌리지 마세요.
- 계산용 audit-balance 스크립트는 통합 후 실제 m7~m12/신규 외형을 중복 합산하지 않게 갱신해주세요. 후보와 런타임의 동일 ID를 비교하고 실제 데이터로 전체 4050 경제를 검증하는 방식이 적합합니다. 계산 보고서를 플레이테스트 결과로 바꾸지 마세요.

## 검증과 응답 형식

기존 테스트 40개는 유지하세요. 이번 소스 묶음에는 토큰 절약을 위해 공통·미션 테스트만 넣었고 네이티브 어댑터 테스트는 생략했습니다. 이름·내용을 약화하거나 버리지 마세요. 테스트가 실행되지 않는 환경이면 미실행으로 표시하세요.

추가 Node 내장 테스트는 다음 행동을 검증해야 합니다.

- 첫 발사 허용, 간격 1ms 전 거부/정확한 경계 허용, 서로 다른 무기로 교체한 직후 우회 불가, 연속 중복 입력, 거부 시 부수 효과 없음.
- 설정/숨김 등 겹친 정지 사유·재개 후 남은 대기, 완료 후/이전 런 거부, 재도전 초기화. 기존 입문·샌드박스 발사는 기존 규칙 그대로.
- m11 한 행성만 반복해선 완료 불가·태양/다른 무기 제외, m12 무기별 일부 충족만으로 완료 불가, 중첩 snapshot 변조가 내부 진척에 영향 없음.
- 기존 v6 기록·코인·스킨·광고 원장 보존, m7~m12 기록/신규 외형 구매·장착·재로드, 첫 완료/광고 보너스 중복 방지, 광고 없이 전체 외형 획득 가능.
- 무제한 입력 속도에서의 간격 처리와 명중 목표를 주입 시계로 검증하되, 타이머 숫자만 늘리는 테스트를 실제 플레이테스트라고 부르지 마세요. Codex가 최종 브라우저 조준·소리·파괴·모바일 QA를 실행합니다.

응답은 간단한 변경 요약, 변경/추가 파일 목록, **변경한 각 파일의 완성된 전체 코드**, 테스트와 미검증 사항 순서로 주세요. 경로를 정확히 쓰고 부분 diff·의사 코드·'이하는 동일'·생략 코드는 금지합니다. 변경하지 않은 플랫폼/네이티브 파일이나 문서를 반복 출력하지 마세요. 코드가 완성된 뒤 응답해주세요.
